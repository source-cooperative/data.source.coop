# ADR-004: Inbound Authentication — OIDC Federation, Platform IdPs, and Role-Based STS Exchange

**Date:** 2026-03-14
**RFC:** RFC-001 §7
**Depends on:** ADR-001
**Language:** ASD-STE100 Simplified Technical English

---

## Context

The data proxy of Source Cooperative must authenticate many different callers:

- **CI/CD pipelines** (GitHub Actions, GitLab CI, Azure DevOps, Terraform Cloud) that ingest or check data
- **Managed compute environments** (Databricks, AWS Lambda, GCP Cloud Run) that process data
- **Interactive developers** who work locally in notebooks, terminals, or the Source Cooperative CLI
- **The Source Cooperative web application** (Next.js on Vercel), which sends requests for authenticated users and for anonymous visitors

ADR-001 specifies that each caller must get short-lived SigV4 session credentials before it sends S3 API calls. This ADR specifies how a caller gets those credentials. It gives the design of the STS exchange endpoint, the identity provider model, and the access scope of a Role.

The industry standard for secretless workload authentication is OIDC workload identity federation. A workload sends a signed JWT from the OIDC provider of its platform to a Security Token Service. That service checks the JWT and returns short-lived scoped credentials. AWS, GCP, Azure, GitHub Actions, GitLab CI, Vercel, and many other platforms support this pattern.

The primary design choice in this ADR is that **each account owns its Roles**. There is no small set of static roles. Each account (an Individual or an Organization) can make Roles that limit the access to its resources. These Roles refer only to platform IdPs. AWS IAM uses the same model: an account configures its own trust policies and roles.

---

## Decision

### Identity Providers (IdPs)

There are two tiers of IdPs.

#### Platform IdPs

The Source Cooperative operators configure the platform IdPs, and users cannot change them. These IdPs are the well-known OIDC issuers of data engineering workflows:

| Platform       | Issuer URL                                    | Key Claims for Constraints                              |
| -------------- | --------------------------------------------- | ------------------------------------------------------- |
| Source Cooperative Auth | `auth.source.coop`                   | `sub`, `groups`                                         |
| GitHub Actions | `https://token.actions.githubusercontent.com` | `repository`, `repository_owner`, `ref`, `environment`, `job_workflow_ref` |
| GitLab CI/CD   | `https://gitlab.com`                          | `project_path`, `ref_type`, `environment`               |
| Azure DevOps   | `https://vstoken.dev.azure.com/<org_id>`      | project, pipeline, environment                          |
| HCP Terraform  | `https://app.terraform.io`                    | `terraform_workspace_id`, `terraform_run_phase`         |
| Vercel         | `https://oidc.vercel.com/<team_slug>`         | `owner`, `project`, `environment`                       |

Each platform IdP has this definition:

```json
{
  "id": "github-actions",
  "issuer_url": "https://token.actions.githubusercontent.com",
  "display_name": "GitHub Actions",
  "well_known_claims": ["repository", "repository_owner", "ref", "environment", "job_workflow_ref"],
  "audience_hint": "https://data.source.coop"
}
```

The `well_known_claims` field is documentation and a hint for the UI. When a user makes a Role binding for this IdP, the UI can suggest these claims as constraints. The `audience_hint` field is the recommended `aud` value. A caller uses that value when it asks for an OIDC token.

This table gives examples. It is not a full list. The platform operators can add a new issuer at any time, and they do not change the code.

> [!NOTE]
> **Future extension: Account-registered IdPs.** The first implementation supports platform IdPs only. We can add IdP registration at the account level later. An account owner can then register a corporate identity system (Okta or Entra ID), a local provider (Keycloak), or any OIDC issuer. This addition changes neither the Role schema nor the STS exchange flow. The `idp` field of a Role already holds an IdP identifier. To let that field refer to an account IdP, we need three things:
>
> 1. A registration API with URL validation that is safe against SSRF.
> 2. A storage table for the account IdPs.
> 3. A guard that prevents the deletion of an IdP while a Role refers to it.
>
> Before then, the platform operators can add a new well-known issuer at any time and do not change the code. This covers the most usual needs.

### Roles

A Role belongs to an account (an Individual or an Organization). A Role specifies two things: **who can assume the Role** (the identity constraints), and **what the credentials of the Role can access** (the permission statements).

A URN identifies each Role: `sc::{account_id}::role/{role_name}`

#### Role Schema

```json
{
  "name": "github-publisher",
  "display_name": "GitHub CI Publisher",
  "max_session_duration": 3600,
  "identity_constraints": [
    {
      "idp": "github-actions",
      "audience": "https://data.source.coop",
      "claim_constraints": [
        {"claim": "repository", "operator": "equals", "value": "my-org/my-repo"},
        {"claim": "ref", "operator": "starts_with", "value": "refs/heads/"}
      ]
    }
  ],
  "permissions": [
    {
      "actions": ["read", "write"],
      "resources": ["sc::my-org::product/climate-data/*"]
    },
    {
      "actions": ["read"],
      "resources": ["sc::my-org::product/reference-data/*"]
    }
  ]
}
```

A Role is a **ceiling** on the permissions that the account already has. The credentials of a Role can never be larger than the access of the account. For each request, the effective permission is the intersection of two sets: the permission statements of the Role, and the account permissions from the policy store (refer to ADR-005).

#### Identity Constraints

Each Role has one or more IdP bindings. Each binding identifies one platform IdP and a set of claim constraints. The JWT that the caller sends must obey these constraints.

**Operators for a claim constraint:**

| Operator | Behaviour | Example |
|----------|-----------|---------|
| `equals` | The strings are the same | `repository` equals `my-org/my-repo` |
| `starts_with` | The string starts with the value | `ref` starts_with `refs/heads/` |

> [!NOTE]
> **Future extension: the `glob` operator.** We considered a glob operator, with a wildcard `*` and a single character `?`, but we deferred it. The `equals` and `starts_with` operators are sufficient for the first use cases, such as a constraint on one repository or on a branch prefix. To add `glob` later is backward-compatible, because it adds a new operator value and does not change the evaluation of the existing constraints. We will add it if users need a wildcard in the middle of a string, for example `refs/heads/release-*`.

Rules:
- The proxy changes each claim value to a string before it compares the values. A JWT claim that is an array or an object evaluates to false.
- The proxy ANDs all constraints in one IdP binding. Each constraint must agree.
- The proxy ORs the IdP bindings of a Role. One binding is sufficient.
- A claim that is not in the JWT evaluates to false. Thus the constraint fails closed.
- The proxy reads only the top-level claims. It does not follow a nested path.

#### Permission Statements

A permission statement specifies what the credentials of the Role can access. A resource pattern has one of these formats:

```
*                                                        → all resources (unlimited ceiling)
sc::{account_id}::product/*                          → all of an account's products
sc::{account_id}::product/{product_name}             → entire product
sc::{account_id}::product/{product_name}/*           → entire product (equivalent)
sc::{account_id}::product/{product_name}/{prefix}/*  → prefix-scoped
sc::{account_id}::product/{product_name}/{key}       → single object
```

Rules:
- A resource pattern can refer to the products of any account. Thus a Role can delegate access to a product of a different account or organisation. The intersection at request time applies the true boundary.
- A resource value of `*` means all resources, thus there is no ceiling. The actual permissions of the account are then the only limit.
- The actions are `read` and `write`. `read` includes `GetObject`, `HeadObject`, and `ListObjects`. `write` includes `PutObject`, `DeleteObject`, and the multipart operations. We can add more specific actions later, for example a separate `upload` and `delete`. A new action value does not break an existing Role definition.
- Permission statements are additive and permit only. There are no explicit denials.

#### Built-in Default Role

Each account has a built-in Role: `sc::{account_id}::role/_default`

- No person can delete it.
- It refers only to the `auth.source.coop` platform IdP.
- Its permissions are `{"actions": ["read", "write"], "resources": ["*"]}`. Thus the ceiling is unlimited, and the actual permissions of the account are the only limit.
- The account owner can add claim constraints to the `auth.source.coop` binding. But the owner cannot change the IdP binding itself.

This Role serves interactive users. Such a user authenticates with `auth.source.coop` and wants full access to all of the resources of the account.

#### Validation of a New Role

1. The `name` field must agree with `[a-z0-9][a-z0-9-]{0,62}`: lowercase letters, digits, and hyphens, with a maximum of 63 characters.
2. Each IdP reference must be the well-known ID of a platform IdP.
3. The `max_session_duration` field must be between 900 and 43200 seconds (15 minutes to 12 hours).
4. There must be a minimum of one identity constraint.
5. There must be a minimum of one permission statement.
6. A Role can have a maximum of 10 IdP bindings, 20 claim constraints for each binding, and 50 permission statements.

#### Role Management API

```
POST   /api/accounts/{account_id}/roles
GET    /api/accounts/{account_id}/roles
GET    /api/accounts/{account_id}/roles/{role_name}
PUT    /api/accounts/{account_id}/roles/{role_name}
DELETE /api/accounts/{account_id}/roles/{role_name}
```

Only an account owner or an organisation admin can manage a Role.

### STS Exchange Endpoint

```
POST /.sts/assume-role-with-web-identity
```

An account name that starts with a dot, such as `.sts`, is invalid. Thus these names cause no route conflict with the S3 API paths.

**Request format:** `application/x-www-form-urlencoded`, compatible with [AWS STS](https://docs.aws.amazon.com/STS/latest/APIReference/):

```
Action=AssumeRoleWithWebIdentity
&WebIdentityToken=<JWT>
&RoleArn=sc::my-org::role/github-publisher
&RoleSessionName=my-ci-job-42
&DurationSeconds=3600
```

**Response format:** XML, compatible with AWS STS:

```xml
<AssumeRoleWithWebIdentityResponse>
  <AssumeRoleWithWebIdentityResult>
    <Credentials>
      <AccessKeyId>SCSTS1...</AccessKeyId>
      <SecretAccessKey>derived-secret</SecretAccessKey>
      <SessionToken>eyJ...</SessionToken>
      <Expiration>2025-03-22T13:00:00Z</Expiration>
    </Credentials>
    <AssumedRoleUser>
      <Arn>sc::my-org::role/github-publisher</Arn>
      <AssumedRoleId>SCSTS1...:my-ci-job-42</AssumedRoleId>
    </AssumedRoleUser>
  </AssumeRoleWithWebIdentityResult>
</AssumeRoleWithWebIdentityResponse>
```

This format makes `boto3.client('sts', endpoint_url='https://data.source.coop/.sts').assume_role_with_web_identity(...)` possible. The AWS SDK sends the `RoleArn` string without a check on the client, thus the URN format of Source Cooperative operates correctly.

### STS Exchange Flow

1. Read the `account_id` and the `role_name` from the `RoleArn`.
2. Load the Role definition from the policy store (cached, 30–60 s TTL).
3. Read the `iss` claim from the JWT, but do not check the signature yet.
4. Compare `iss` with the permitted IdPs of the Role. If no IdP agrees, refuse the request immediately.
5. Get the JWKS of the IdP that agrees (cached, 1 hour TTL, 3 s timeout). If the fetch fails, use the stale copy.
6. Check the JWT signature, `exp`, `nbf` (with a clock difference of 60 seconds), and `aud`.
7. Evaluate the claim constraints of the IdP binding that agrees.
8. Make sure that `DurationSeconds` is not more than the `max_session_duration` of the Role.
9. Make the credentials (ADR-001 gives the token structure) and send the response.

The Role URN is mandatory. The caller must know which Role to assume, because the system does not examine all Roles to find one that agrees. Thus the lookup stays at O(1) and is deterministic. AWS uses the same pattern: `AssumeRoleWithWebIdentity` also needs a Role ARN.

### JWKS Cache

- Cache key: the issuer URL in a canonical form
- TTL: 1 hour
- Stale copy: if the JWKS fetch fails and there is a cached copy, use that copy for a maximum of 24 hours and write a warning to the log
- If there is no cached copy and the fetch fails, return `IDPCommunicationError`
- Maximum response body: 256 KB

A distributed deployment has many Workers isolates. Each isolate keeps its own JWKS cache. During a key rotation at an IdP, two isolates can hold different versions of the JWKS of that issuer. This is unlikely to cause a problem. An OIDC provider publishes a new key well before it retires the old key, and the TTL of 1 hour keeps each cache sufficiently fresh. If we see temporary failures during the key rotations of an IdP, we can add a shared cache tier such as Workers KV.

### Error Responses

Each error uses the XML format of AWS STS, for compatibility with the SDKs:

```xml
<ErrorResponse>
  <Error>
    <Code>InvalidIdentityToken</Code>
    <Message>JWT claims do not satisfy the identity constraints for role 'github-publisher'</Message>
  </Error>
</ErrorResponse>
```

| Condition | Error Code | HTTP Status |
|-----------|-----------|-------------|
| Role URN malformed | `MalformedPolicyDocument` | 400 |
| Role not found | `InvalidParameterValue` | 400 |
| JWT malformed or unparseable | `InvalidIdentityToken` | 400 |
| JWT issuer matches no IdP on Role | `InvalidIdentityToken` | 400 |
| JWT signature verification failed | `InvalidIdentityToken` | 400 |
| JWT expired | `ExpiredTokenException` | 400 |
| JWT `aud` mismatch | `InvalidIdentityToken` | 400 |
| Claim constraints not satisfied | `InvalidIdentityToken` | 400 |
| IdP JWKS endpoint unreachable | `IDPCommunicationError` | 400 |
| `DurationSeconds` exceeds max | `ValidationError` | 400 |

Each error message identifies the condition that failed. But it does not show the expected value of a constraint. The message contains the Role name, because the caller already knows it: the caller gave that name in the request. The message does not contain the constraint values, such as the expected repository or the expected ref pattern. Thus the message does not show the trust policy of the Role to a caller who has no permission. The server-side audit log contains the full data about the constraint that failed, and an account admin can read it.

### Observability

Each STS exchange writes a structured log entry. This is true for a success and for a failure:

```json
{
  "event": "sts_exchange",
  "timestamp": "2025-03-22T12:00:00Z",
  "account_id": "my-org",
  "role_name": "github-publisher",
  "role_urn": "sc::my-org::role/github-publisher",
  "idp_issuer": "https://token.actions.githubusercontent.com",
  "assumed_by": "repo:my-org/my-repo:ref:refs/heads/main",
  "session_name": "my-ci-job-42",
  "result": "success",
  "access_key_id": "SCSTS1...",
  "duration_seconds": 3600,
  "client_ip": "...",
  "failure_reason": null
}
```

Each S3 request with STS credentials also writes a log entry. That entry contains the `account_id`, the `role_name`, the `session_name`, the `assumed_by` field, the action, the resource, and the result.

### Identity Source: Source Cooperative Auth (`auth.source.coop`)

The auth system of Source Cooperative uses Ory and issues standard OIDC tokens. `auth.source.coop` is a platform IdP. An interactive user authenticates with this IdP and assumes the `_default` Role of the account. That Role passes through all of the permissions of the account.

This path is applicable to:
- Interactive local development. The developer exchanges a browser session token.
- The CLI `source login` flow: a browser device flow gives an Ory token, and the CLI does the STS exchange.
- The client-side exchange in Next.js, for authenticated web users.

### Next.js and Front-End Authentication

**Authenticated users:** The browser holds the Ory session token. The client sends the token to `/.sts` with the `_default` Role of the user and gets short-lived session credentials. The browser then sends the S3 API calls directly to the proxy.

**Anonymous visitors:** The Next.js server uses its Vercel OIDC token to get credentials. It uses a Role that the platform specifies, and that Role permits read-only access to public products. All anonymous traffic goes through the full middleware stack of the proxy.

**Admin users:** Admin users use the same flow as authenticated users. The account permissions in the policy store give the admin capabilities. There is no special role type.

### CLI and SDK Support

**`source-coop` CLI:**

The existing `source-coop-cli` does the authentication and holds the credentials. A user puts one profile for each role in `~/.aws/config`:

```ini
[profile source-read]
credential_process = source-coop creds --role-arn sc::my-org::role/reader

[profile source-write]
credential_process = source-coop creds --role-arn sc::my-org::role/publisher
```

The `source-coop creds` command looks for valid credentials in its cache. If it finds none, it starts an OIDC login, calls the STS endpoint, and returns the credentials in the JSON format of `credential_process`.

**GitHub Action: `source-cooperative/configure-credentials`**

```yaml
permissions:
  id-token: write
steps:
  - uses: source-cooperative/configure-credentials@v1
    with:
      role-urn: sc::my-org::role/github-publisher
  - run: aws s3 cp data.parquet s3://data.source.coop/my-org/my-product/
```

The action asks for a GitHub OIDC token with the audience `https://data.source.coop`. It then calls the STS endpoint and writes `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_SESSION_TOKEN` into the environment. All downstream tools then read these variables automatically.

**Direct SDK usage:**

```python
sts = boto3.client('sts', endpoint_url='https://data.source.coop/.sts')
creds = sts.assume_role_with_web_identity(
    RoleArn='sc::my-org::role/github-publisher',
    WebIdentityToken=token,
    RoleSessionName='my-job'
)
```

## Consequences

**Benefits**

- Each account owns its Roles. An operator does nothing when a user makes a new access scope.
- The system accepts any OIDC issuer in the platform list, and we do not change the code. We can add IdP registration at the account level later.
- All credential paths use the same `/.sts` endpoint. Thus there is one code path to check a token and to issue a credential.
- The Role-as-ceiling model prevents an increase of privilege. A Role can never give more access than the account has.
- The request and response formats are compatible with AWS STS. Thus an existing AWS SDK operates with a custom endpoint URL.
- Claim constraints give precise control over the workloads that can assume a Role. For example, a Role can accept only GitHub Actions from one repository and one branch.
- A CI/CD or managed compute workflow with an ambient OIDC token keeps no secret.
- The operational credentials are short-lived, and the authentication method of the caller makes no difference.
- The error messages are detailed and useful for debug work. But they show no sensitive data.

**Costs and Risks**

- The `/.sts` endpoint is on the critical path to start a session. Its availability and its latency have a direct effect on each new session.
- The JWKS fetch and cache must be robust. If a JWKS is stale or not available, each exchange for that issuer fails.
- At first, the system supports only the platform IdPs. An account that needs a corporate identity system (Okta or Keycloak) must ask the platform operator to add the issuer. Or the account must wait for IdP registration at the account level (refer to the future-extension note above).
- The claim constraint language is deliberately minimal: `equals` and `starts_with`. It does not support complex matches such as glob patterns, numeric comparisons, or set membership. We can extend it later (refer to the `glob` future-extension note).
- Only an operator can add a new platform IdP. This is a governance decision, and not a self-service action.

## Alternatives Considered

**Account-registered IdPs (self-service)** — deferred. This lets an account register a corporate Okta, a local Keycloak, or any OIDC issuer, and an operator does nothing. But it adds an SSRF risk, because the proxy then fetches a JWKS from a URL that a user controls. It also adds DNS rebinding risks and questions about trust in a self-asserted identity. The platform IdP list covers the primary use cases. We can add IdP registration at the account level when the demand occurs.

**A fixed role set (`anonymous`, `authenticated_user`, `admin`)** — rejected. It is not sufficient for delegation. An account must make a Role for a specific resource and a specific IdP. For example: "GitHub Actions from repository X can write to dataset Y." A fixed role set cannot express this.

**IdP-first resolution, with no Role URN** — rejected. The system must then examine all Roles of all accounts to find the Roles that agree with the issuer of a JWT. This is ambiguous when more than one Role agrees. When the caller gives the Role, the lookup stays at O(1) and is deterministic.

**Claim constraints on the IdP registration and not on the Role** — rejected. Claim constraints belong on the Role, because two Roles of one account can need different constraints for the same IdP. For example, one Role for GitHub Actions accepts only `refs/heads/main`, and a second Role accepts any branch.

**API keys for environments with no OIDC** — refer to ADR-008. These keys are long-lived JWTs with a signature from the OIDC issuer of the proxy. A caller exchanges such a key at `/.sts` in the same way as any other token. They serve university HPC clusters, on-premises instruments, and other environments with no ambient OIDC token and no browser access.

**RFC 8693 token exchange ("act-as") for server-side Next.js requests** — considered, and rejected for the first implementation. To pass the Ory token of the user through the client is more simple, and it gives the same access metrics. The audit logs can later need to show a difference between two cases: "the user accessed the data directly" and "Next.js accessed the data for the user". Then we can examine this alternative again.
